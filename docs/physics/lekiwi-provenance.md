# LeKiwi Phase 5B physical provenance

Work package: **P5B — LeKiwi mobile manipulation** (with P6 WebMCP preservation and P7 evidence
discipline). This document records where every physical parameter came from, what is estimated,
what is calibration-required, and exactly what the resulting capability claim does and does not
cover.

**Claim after P5B:** numerically verified flat-floor LeKiwi mobile manipulation in the browser
MuJoCo workspace.

```text
backend:    browser-mujoco
capability: single-authority LeKiwi V1 flat-floor holonomic mobile-manipulation workspace with
            explicit passive omni-wheel rollers, a free payload, live async Python and causal
            task evaluation
evidence:   numerically-verified
```

No hardware comparison was performed, and none is claimed.

## 3. Frames

The pinned URDF root link is `base_plate_layer1-v5`. Its `+X` points toward the right-hand wheel
side and `+Y` toward the arm mount. The physical package is authored in the **LeRobot body frame**
(x forward, y left, z up), with the origin at the centroid of the three wheel centres, at wheel
axle height:

```text
model_x = urdf_y      model_y = -urdf_x      model_z = urdf_z         (a +90 deg rotation about Z)
model frame origin in the URDF frame = (0.000231, -0.006533, 0.017860) m
floor at model z = -0.0508 m for the base scenes (= -wheel radius)
```

Forward is `+Y` in the URDF frame. That reading is supported three independent ways: the wheel the
source names `base_back_wheel` sits at `-Y`; the arm mounts at `+Y`; and with this convention the
three source wheel axes reproduce the pinned LeRobot Kiwi mapping angles exactly.

The canonical display mesh is baked in that pinned URDF root frame, whereas the MuJoCo free body
uses the wheel-centroid LeRobot frame above. The physical renderer therefore applies the audited
fixed URDF→model yaw and root-origin offset to every observed base pose before drawing the mesh.
Displayed wheel spin comes from the observed MuJoCo wheel `qpos`; because the physical joints use
the LeRobot-positive axes that are anti-parallel to the source URDF wheel axes, only the visual
angle sign is reversed. These transforms are presentation-only and never feed state back to MuJoCo.

The canonical arm mesh and the physical arm are also pinned from two different source chains: the
LeKiwi URDF visual and Menagerie SO-ARM101 respectively. Their joint zero/sign conventions are not
identical. P5B therefore records an explicit physical→canonical presentation map (source code:
`LEKIWI_CANONICAL_PRESENTATION_MAP`). Corresponding shoulder/elbow/wrist pivots were reconciled
from the two pinned kinematic chains; wrist roll was checked independently using the downstream
gripper-hinge axis. This conversion changes only the displayed mesh angles. Physical joint state,
contacts, task evaluation, live Python, and WebMCP remain the unmodified MuJoCo observations.

## 5. Audited source discrepancies

1. **Wheel axis sign convention.** The pinned URDF `base_*_wheel` `<axis>` values are
   *anti-parallel* to the LeRobot motor positive-velocity convention. With the URDF axes taken at
   face value, every wheel's rotation moment arm about the base centre comes out negative, which
   contradicts the `+base_radius` column of the pinned LeRobot mapping. Negating all three axes
   makes the geometry agree with the pinned mapping **exactly**: the drive directions land on
   150° / −90° / 30° for left/back/right to machine precision, and all three moment arms become
   positive. The model packages therefore declare the LeRobot-positive axis and record
   `sourceUrdfAxis` alongside it; the core test asserts the anti-parallel relationship through the
   declared frame map.
2. **LeRobot controller defaults are not measured robot dimensions.** `wheel_radius = 0.05 m` and
   `base_radius = 0.125 m` are interface parameters. The source geometry gives 0.0508 m and
   0.1098–0.1198 m. Both parameter sets are implemented (`SOURCE_PARAMETERS`,
   `LEROBOT_DEFAULT_PARAMETERS`); the physical controller uses the source-derived set, and a test
   asserts that the two agree in sign on every primitive and stay within a ±15 % magnitude band.
3. **LeRobot raw wheel limits are software limits.** `max_raw = 3000` bounds the interface, not the
   motor. It is used as the actuator control range and labelled as such.
4. **URDF inertials use CAD default densities.** See §7.
5. **A top-down rim grasp is not kinematically reachable** for the SO-ARM101 at this bench height:
   `arm_wrist_flex` and `arm_wrist_roll` both saturate before the tool axis reaches vertical. The
   physical grasp uses a 50° tilted rim-wall pinch instead. This is a documented repair of the
   legacy grasp pose, not a change to the robot physics.
6. **The legacy blocked-cell list conflicts with the pinned bench footprint** and with the physical
   LeKiwi footprint (≈0.15 m radius vs 0.05 m planner cells). The legacy scenario itself states
   "point-cell occupancy only; the frozen planner does not provide a footprint-clearance
   guarantee." The occupancy grid and A* are preserved as a *desired-route generator*, with the
   blocked set repaired to the bench envelope plus the visible restricted stop, inflated by the
   base footprint radius. Route completion is never taken from the planner.
7. **The legacy service-base stop at (600, 0, 500) mm is out of arm reach** (0.361 m from the
   beaker, beyond a comfortable SO-ARM101 working distance at that height). It is repaired to
   `(0.274, 0.030) m, yaw −90°`, from which both the pickup and the delivery pose are reachable
   with sub-2 mm IK residual.

## 6. Wheel and contact formulation

**No reduced omniwheel contact model is used.** Every omni wheel in every LeKiwi package carries
its twelve source-count rollers as individually hinged passive bodies:

```text
wheel body (local z = spin axis, local x = world up, local y = drive direction)
├── hub cylinder            r 0.030 m, half-width 0.019414 m, mass 0.401661 kg, non-colliding
├── row a: 6 rollers at 60° spacing, z = +0.009707 m
└── row b: 6 rollers at 60° spacing, staggered 30°, z = −0.009707 m
        each roller: hinge about the tangential axis, ellipsoid barrel
        (0.009707, 0.009707, 0.0205) m, mass 0.0793853 kg, condim 3, friction 0.85
```

Consequences, all of which are gated:

* Traction along the driven direction comes from the roller/ground contact of whichever roller is
  in contact, not from a friction coefficient chosen to make an animation look right.
* Low resistance along the passive (axle) direction comes from the roller hinges spinning freely.
* Removing ground contact removes propulsion, because there is nothing for the wheel to react
  against.

Sections 28 of the governing plan (reduced-model vs reference comparison) **does not apply**: the
browser robot and the reference rig use the same explicit roller formulation, so there is no
reduction to justify. The single-wheel reference rig still exists and is used to characterize the
contact behaviour directly.

Why the obvious cheaper reduction was rejected: MuJoCo's plane-primitive contact frame is fixed in
the world frame regardless of the wheel's yaw (verified directly — a cylinder yawed 0°, 30° and 90°
on a plane produced the identical contact tangent basis). Anisotropic `friction` on a cylinder
therefore cannot represent an omni wheel whose passive direction rotates with the chassis.

## 7. The CAD-density caveat

The pinned URDF assigns CAD default densities. The resulting figures are internally consistent and
genuinely source-derived, but they are not a weighed robot:

* chassis composite 6.659 kg, wheels 1.354 kg each → **10.72 kg base**, ≈2× a plausible assembled
  LeKiwi;
* the `ST3215_Servo_Motor` links are ≈0.066 kg, which *is* the real ST3215 mass, while the plates
  and 3D-printed parts are several times too heavy — so no single scale factor corrects it.

The package preserves the URDF values unscaled rather than substituting an invented mass, and
states the consequence: **absolute mass, traction margin, motor loading, payload rating, and
acceleration limits are calibration-required.** The P5B gates establish causal behaviour of this
declared simulation model (motion arises from contact; a lifted base does not move; reduced
traction degrades propulsion; a payload is carried by contact). They do **not** establish
hardware-accurate acceleration, traction margin, motor loading, stopping distance, or payload
performance, because the absolute mass/inertia and several contact parameters remain uncalibrated.

The arm is the exception: the URDF's CAD-density arm subtree is 6.60 kg, which the SO-ARM101's
STS3215 servos could not hold. The arm therefore uses the pinned Menagerie `robotstudio_so101`
inertials (0.632 kg total) — a better source for the same hardware, already pinned by this
repository.

## 8. Control architecture

```text
public LeRobot action  {x.vel m/s, y.vel m/s, theta.vel deg/s}
        ↓ deg/s → rad/s at the public boundary
pinned LeRobot Kiwi mapping, source-derived per-wheel geometry
   wheel_linear_i = vx·d_ix + vy·d_iy + ω·R_i        d = drive direction, R = moment arm
   wheel_angular_i = wheel_linear_i / 0.0508
        ↓ proportional saturation at ±4.60061 rad/s (LeRobot's rule: scale all three)
bounded MuJoCo velocity servo   kv 2.2, forcerange ±2.94 N·m
        ↓
wheel torque → roller/ground contact → actual base motion (MuJoCo free body)
```

Nothing writes base pose or base velocity. The only `qpos` assignment in
`src/physics/lekiwi-mujoco-worker.js` is inside `applyDeclaredInitialState`, the declared
setup/reset path; there is no `qvel` assignment at all. The models declare zero equality
constraints, and the worker refuses to load a LeKiwi model that has any.

The arm uses bounded position servos with the pinned Menagerie STS3215 parameters
(`kp 998.22`, `kv 2.731`, `forcerange ±2.94 N·m`).

## 9. Observation cadence

**10 ms (5 physics steps at the 0.002 s timestep).** This is a software observation parameter, not
a hardware sensor rate. It was measured against this task's causal events rather than inherited
from OpenArm's 2 ms:

| Event that must be resolved | Measured duration (native, 1 ms) |
|---|---|
| worktop support contact overlapping a still-closed rim pinch | ≈1.45 s |
| settle dwell required by the evaluator | 0.25 s |
| gripper close transition | ≈1.0 s |
| controller period | 20 ms |

A 10 ms cadence provides 25 samples across the 0.25 s evaluator settle dwell and two samples per
20 ms controller period; the measured support/closed-grip overlap is much longer. The full courier
produces ≈3 270 authoritative samples per browser run.

## 11. Evidence classification (P7)

Three separate things, kept separate:

1. **Software verification** — model loading, address resolution, unit and frame handling, mapping
   signs, API surface, scheduling, lifecycle. Covered by `tests/physics/lekiwi-phase5b-core.mjs`
   and the worker's own compiled-model assertions.
2. **Numerical / model verification** — the chosen formulation behaves coherently, the physical
   gates hold, and halving the timestep does not change any declared conclusion. Covered by
   `native/lekiwi_reference.py` and `tests/lekiwi-conformance-browser.spec.mjs`.
3. **Hardware comparison** — **not performed.** Browser/native agreement is implementation
   evidence only: both backends run the same pinned model and the same approximations.

## 12. Capability limitations

Validated only on a declared flat indoor floor with the declared parameters above. Nothing here
establishes, and nothing may be claimed about:

carpet, thresholds, curbs, ramps, rough or outdoor terrain, suspension, high-speed carrying,
aggressive manoeuvres, wheel wear, battery droop, motor thermal behaviour, network timing, real
odometry, SLAM or autonomous navigation, payload rating, real gripping force, glass compliance,
liquid or thermal behaviour, force/tactile sensing, or hardware safety.
